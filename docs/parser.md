# Парсер spec-файлов

## Что делает модуль

parser.py извлекает из .spec-файлов ключевую информацию, необходимую для дальнейшего анализа зависимостей и построения плана сборки.

На вход модуль получает путь к директории со .spec-файлами.

В результате работы для каждого spec-файла формируется структура PackageSpec, содержащая:
- имя главного пакета (name);
- множество предоставляемых возможностей (provides), включая:
    - само имя пакета;
    - имена всех субпакетов (%package);
    - явные Provides: из spec-файла;
- множество зависимостей, необходимых для сборки (build_requires), извлечённых из BuildRequires.

Кроме того, для всей директории строится обратный индекс provides_index, отображающий каждую capability на множество пакетов, которые её предоставляют.

## Основная идея

.spec-файлы содержат метаинформацию о пакете, но не в удобном для обработки виде. parser.py использует библиотеку specfile для парсинга, а затем преобразует полученные данные в простые структуры Python.

Процесс разбора одного файла включает:
- Извлечение имени – считывается поле Name: с раскрытием макросов (например, %{?cross}binutils%{?_with_debug:-debug} превращается в binutils).
- Сбор предоставляемых возможностей – добавляется само имя пакета, а затем анализируются:
    - явные Provides: теги;
    - субпакеты (%package): имена субпакетов (main_name-subname или полное имя через -n) также попадают в provides.
- Сбор зависимостей для сборки – извлекаются BuildRequires:, при этом:
    - отбрасываются версионные ограничения (например, >= 2.24)
    - отбрасываются зависимости, заданные как пути к файлам (например, /usr/bin/pod2man)
    - отбрасываются нераскрытые макросы (например, %{name}-devel)
- После обработки всех файлов строится provides_index: для каждой capability сохраняется множество пакетов, которые её предоставляют.

Такой подход даёт возможность на следующих этапах (resolve) по абстрактной зависимости (например, pkgconfig(zlib)) найти конкретный пакет, который ее предоставляет (например, zlib-devel)

## Структура данных

### PackageSpec
```
@dataclass
class PackageSpec:
    name: str                     # имя главного пакета
    provides: set[str]            # все предоставляемые возможности
    build_requires: set[str]      # зависимости для сборки (имена пакетов)
    source_file: Path | None      # путь к исходному .spec-файлу (для отладки)
```
### provides_index
```
# capability → множество имён пакетов-провайдеров
index: dict[str, set[str]]
```
Например, для двух пакетов binutils и gcc, предоставляющих bundled(libiberty), индекс будет содержать запись: "bundled(libiberty)": {"binutils", "gcc"}

## Обработка субпакетов
Субпакеты описываются секциями %package. Имя субпакета вычисляется так:

- %package c++ -> main_name-c++ (суффикс через дефис);
- %package -n libgcc -> libgcc (полное имя через флаг -n);
- пустые опции соответствуют главному пакету – не добавляются.

Имя субпакета, а также явные Provides: внутри его секции добавляются в provides основного PackageSpec. Это позволяет в дальнейшем разрешать зависимости на субпакеты (например, myapp-devel).

## Особенности парсинга

- Версии отбрасываются – BuildRequires: gcc >= 11.2.0 превращается в gcc. Это соответствует упрощению для MVP

- Пути отбрасываются – зависимости вида /usr/bin/pod2man или libfoo.so.1 игнорируются, так как их разрешение потребовало бы парсинга %files секций.

- Нераскрытые макросы отбрасываются – BuildRequires: %{name}-devel не попадает в build_requires, поскольку макрос не может быть сопоставлен с реальным пакетом.

- Многострочные зависимости – обрабатываются корректно благодаря specfile.

- Зависимости через запятую – поддерживаются через разбиение по запятым.


## Зависимости и установка
- Python-библиотека: specfile (pip install specfile).

- Системные RPM-биндинги: для Ubuntu – apt install python3-rpm, для Fedora – dnf install python3-rpm.

## Использование

### Запуск из командной строки

./specs - директория со .spec-файлами для парсинга

```bash
# Базовый запуск
python3 parser.py ./specs

# С игнорированием ошибочных файлов
python3 parser.py ./specs --ignore-errors
```

### Формат вывода:

Программа выводит JSON в stdout. Структура:

```
{
  "packages": {
    "имя_пакета": {
      "provides": [список предоставляемых возможностей],
      "build_requires": [список зависимостей для сборки],
      "source_file": "путь_к_файлу.spec"
    }
  },
  "provides_index": {
    "capability_1": ["пакет_A", "пакет_B"],
    "capability_2": ["пакет_C"]
  }
}
```

## Взаимодействие с другими модулями

resolve использует specs и provides_index для выбора provider'ов и построения замыкания зависимостей.

planner получает от resolve уже конкретные зависимости и строит граф сборки.

Таким образом, parser.py обеспечивает первый, фундаментальный слой: превращает сырые .spec-файлы в структурированные данные, которые затем анализируются и преобразуются в план сборки
