# Planner: обработка циклов зависимостей

## Что делает модуль

`planner.py` строит план сборки по уже известному множеству пакетов `to_build` и зависимостям между ними.

Ребро `A -> B` означает,что пакет `A` требует `B` для сборки,то есть `B` должен быть собран раньше.

## Основная идея

В исходном графе зависимостей могут быть циклы. Обычная топологическая сортировка на таком графе не работает.

Поэтому планировщик:

1. строит граф зависимостей между пакетами;
2. ищет сильно связные компоненты (SCC) алгоритмом Тарьяна;
3. помечает компоненты размера больше 1,а также вершины с завиясмостями с собой,как циклические;
4. схлопывает SCC в этапы сборки;
5. строит граф этапов;
6. выполняет топологическую сортировку графа этапов.

После схлопывания SCC граф этапов является ацикличным.

## Что считается результатом

Результат работы planner `BuildPlan`,содержащий:

- граф пакетов;
- найденные компоненты;
- список этапов сборки;
- зависимости между этапами;
- для циклических этапов внутренние ребра и пометку,что требуется bootstrap-обработка.

## Почему цикл не считается ошибкой

Цикл в BuildRequires не обязательно означает невозможность сборки. Он означает,что обычной топологической сортировки недостаточно.

planner не пытается автоматически разорвать цикл,а выделяет его в отдельный `cycle` stage и сохраняет внутреннюю структуру цикла для следующего этапа обработки.

## Пример

Для пакетов `gcc`,`glibc`,`binutils` и зависимостей

- `gcc -> glibc`
- `gcc -> binutils`
- `glibc -> gcc`

planner находит две компоненты:

- `binutils` - ацикличная;
- `gcc`,`glibc` - циклическая.

После этого получается два этапа:

1. `binutils`
2. `gcc + glibc` как cycle-stage,зависящий от первого этапа

## Текущие ограничения

Текущая реализация не:

- строит внутренний порядок внутри cycle-stage;
- не выполняет bootstrap-сборку;
- не работает с версиями зависимостей;

## Как это может быть реализовано дальше

На следующем этапе системы для каждого `cycle` stage может использоваться отдельный обработчик bootstrap-циклов `bootstrap handler`

Его задача - не заново искать цикл,а получить от `planner` уже найденный `cycle` stage и преобразовать его во внутренний исполнимый план сборки,состоящий из нескольких подэтапов.

### Что получает bootstrap handler на вход

Например,после работы `planner` циклический этап может выглядеть так:

```json
{
  "id": 1,
  "packages": ["gcc","glibc"],
  "type": "cycle",
  "depends_on": [0],
  "internal_edges": [
    ["gcc","glibc"],
    ["glibc","gcc"]
  ],
  "bootstrap_required": true
}
```

Здесь:

- `packages` - пакеты внутри циклической компоненты;
- `depends_on` - внешние этапы,которые должны быть выполнены раньше;
- `internal_edges` - внутренние зависимости внутри цикла;
- `bootstrap_required` - явная пометка,что обычной топологической сортировки здесь недостаточно.

### Что должен делать bootstrap handler

Bootstrap handler получает такой `cycle` stage и строит для него внутренний staged-план.

В общем виде его работа может выглядеть так:

1. получить список пакетов внутри цикла и внутренние зависимости между ними;
2. определить,какой пакет или набор пакетов можно использовать для временного разрыва цикла;
3. построить несколько bootstrap-подэтапов;
4. вернуть уже ацикличный внутренний план.

### Что значит временно разорвать цикл

Идея состоит в том,что один из пакетов сначала собирается не в полном,а в упрощённом bootstrap-варианте,достаточном для продолжения сборки остальных пакетов циклической компоненты.

После этого:

- остальные пакеты цикла собираются с использованием bootstrap-артефактов;
- затем временно упрощённый пакет пересобирается в полном режиме;
- при необходимости выполняется дополнительная полная пересборка других пакетов компоненты.

То есть внутри `cycle` stage итоговый порядок имеет вид не одной топологической сортировки пакетов,а последовательности внутренних подэтапов.

### Пример возможного результата работы bootstrap handler

Для цикла между `gcc` и `glibc` внутренний план может выглядеть,например,так:

```json
{
  "cycle_stage_id": 1,
  "substages": [
    {
      "id": "1.1",
      "packages": ["gcc-bootstrap"],
      "depends_on": []
    },
    {
      "id": "1.2",
      "packages": ["glibc"],
      "depends_on": ["1.1"]
    },
    {
      "id": "1.3",
      "packages": ["gcc"],
      "depends_on": ["1.2"]
    }
  ]
}
```

Здесь:

- `gcc-bootstrap` - условное обозначение минимального bootstrap-варианта пакета;
- сначала собирается временная bootstrap-версия `gcc`;
- затем собирается `glibc`;
- после этого собирается полноценный `gcc`.

### Как это встраивается в общий BuildPlan

После обработки цикла один `cycle` stage может быть заменён внутренним ацикличным подграфом подэтапов.

Например,если исходный верхнеуровневый план был таким:

```json
{
  "stages": [
    {
      "id": 0,
      "packages": ["binutils"],
      "type": "acyclic",
      "depends_on": []
    },
    {
      "id": 1,
      "packages": ["gcc","glibc"],
      "type": "cycle",
      "depends_on": [0],
      "internal_edges": [
        ["gcc","glibc"],
        ["glibc","gcc"]
      ],
      "bootstrap_required": true
    }
  ]
}
```

то после работы bootstrap handler итоговый план может быть уточнён так:

```json
{
  "stages": [
    {
      "id": 0,
      "packages": ["binutils"],
      "type": "acyclic",
      "depends_on": []
    },
    {
      "id": "1.1",
      "packages": ["gcc-bootstrap"],
      "type": "bootstrap",
      "depends_on": [0]
    },
    {
      "id": "1.2",
      "packages": ["glibc"],
      "type": "bootstrap",
      "depends_on": ["1.1"]
    },
    {
      "id": "1.3",
      "packages": ["gcc"],
      "type": "bootstrap",
      "depends_on": ["1.2"]
    }
  ]
}
```

### Почему это вынесено в отдельный этап

Обычный `planner` может по графу зависимостей определить,что цикл существует,но не может в общем случае автоматически определить,как именно его разрывать.

Для этого обычно нужна дополнительная информация,например:

- существует ли для пакета bootstrap-конфигурация;
- какой пакет допустимо собирать в минимальном виде;
- какие зависимости можно временно ослабить;
- требуется ли после этого одна или несколько полных пересборок.

Поэтому архитектурно разумно разделить ответственность так:

- `planner` отвечает за поиск SCC,выделение `cycle` stages и построение ацикличного графа этапов верхнего уровня;
- `bootstrap handler` отвечает за раскрытие `cycle` stage во внутренний исполнимый staged-план.

Таким образом,`cycle` stage - это не окончательный порядок сборки,а промежуточное представление проблемной циклической компоненты,которое затем должно быть преобразовано в последовательность bootstrap-подэтапов.
