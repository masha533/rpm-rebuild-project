# Документация по `bootstrap_handler.py`

## Назначение модуля

`bootstrap_handler.py` отвечает за обработку циклических компонент зависимостей после того, как `planner.py` уже:

- построил граф зависимостей пакетов;
- нашёл SCC;
- построил DAG между компонентами;
- пометил циклические компоненты как `type = "cycle"`.

Сам `planner.py` **не разрывает цикл внутри**. Он только говорит: вот компонента циклическая, вот её пакеты, вот её внешние зависимости

Задача `bootstrap_handler.py` — взять такую `cycle-stage` и превратить её во **внутренний ациклический план этапов**.

---

## Идея обработки цикла

Для каждой циклической компоненты используется трёхшаговая схема:

1. `bootstrap(pkg)` — начальная сборка пакета;
2. `full(pkg)` — полная сборка пакета;
3. `final(pkg)` — финальная пересборка только для тех пакетов, у которых на предыдущих шагах были отложенные внутренние зависимости.

Смысл такой:

- на этапе `bootstrap` зависимости на более поздние пакеты цикла временно откладываются;
- на этапе `full` используются уже собранные `full`-версии более ранних пакетов и `bootstrap`-версии более поздних;
- на этапе `final` достраиваются пакеты, которые раньше ещё опирались на отложенные внутренние зависимости.

Это позволяет превратить одну циклическую компоненту в набор стадий, который уже является DAG.

---

## Входные данные

Модуль работает с планом, который уже построен `planner.py`.

Пример входного плана:

```json
{
  "packages_graph": {
    "binutils": [],
    "gcc": ["binutils", "glibc"],
    "glibc": ["gcc"]
  },
  "stages": [
    {
      "id": 0,
      "packages": ["binutils"],
      "type": "acyclic",
      "depends_on": [],
      "internal_edges": [],
      "bootstrap_required": false
    },
    {
      "id": 1,
      "packages": ["gcc", "glibc"],
      "type": "cycle",
      "depends_on": [0],
      "internal_edges": [["gcc", "glibc"], ["glibc", "gcc"]],
      "bootstrap_required": true
    }
  ]
}
```

## Функции модуля

### `choose_bootstrap_order(component, graph)`

Выбирает порядок пакетов внутри одной циклической компоненты.

#### Что делает

На каждом шаге выбирается пакет:

1. с минимальным числом зависимостей на ещё не выбранные пакеты этой же компоненты;
2. если есть несколько таких пакетов — раньше выбирается тот, от которого зависит больше других пакетов в оставшейся части компоненты;
3. если и здесь равенство — используется лексикографический порядок имён.

#### Зачем это нужно

Внутри цикла нет естественного топологического порядка, 
потому что все пакеты зависят друг от друга напрямую или косвенно. Поэтому вводится правило выбора порядка bootstrap-сборки.

#### Пример

Для графа:

```python
{
    "gcc": {"glibc", "binutils"},
    "glibc": {"gcc"},
    "binutils": set(),
}
```

и компоненты:

```python
["gcc", "glibc"]
```

функция вернёт, например:

```python
["gcc", "glibc"]
```

---

### `expand_cycle_stage(stage, graph, external_dep_stage_ids, start_stage_id)`

Разворачивает одну стадию типа `cycle` во внутренний набор стадий.

#### Что делает

Для одной циклической компоненты строит:

- bootstrap-этапы по одному пакету;
- full-этапы по одному пакету;
- final-этапы только для тех пакетов, где раньше были отложенные внутренние зависимости.

#### Основная логика

##### Шаг 1. `bootstrap`

Для каждого пакета `pkg`:

- берутся все внутренние зависимости внутри текущей SCC;
- зависимости на более ранние пакеты в выбранном порядке можно уже учитывать;
- зависимости на более поздние пакеты временно откладываются.

То есть `bootstrap(pkg)` зависит:

- от внешних стадий компоненты;
- от bootstrap-стадий более ранних пакетов цикла.

##### Шаг 2. `full`

Для каждого пакета `pkg`:

- используется его собственный bootstrap-этап;
- для более ранних пакетов цикла используются уже full-этапы;
- для более поздних пакетов — bootstrap-этапы.

##### Шаг 3. `final`

Если у пакета были отложенные внутренние зависимости, добавляется финальный этап, 
который пересобирает пакет уже после того, как соответствующие внутренние зависимости доступны в более полном виде.

#### Зачем нужен `final`

`full`-этап может всё ещё использовать bootstrap-версии более поздних пакетов. `final` нужен, чтобы «дозакрыть» такие случаи.

---

### `apply_bootstrap(plan)`

Главная функция модуля.

#### Что делает

Берёт план от `planner.py` и проходит по его стадиям:

- `acyclic`-стадии просто копируются в новый план;
- `cycle`-стадии разворачиваются функцией `expand_cycle_stage(...)`.

#### Важная деталь

Если старая стадия развернулась в несколько новых, то все последующие зависимости на неё переводятся на **последнюю** стадию этой группы, потому что именно она означает завершение обработки всей исходной компоненты.

#### Пример

Если исходная стадия `id = 1` превратилась в стадии:

```python
[1, 2, 3, 4, 5]
```

то зависимость на старую стадию `1` заменяется на зависимость на новую стадию `5`.

---

## Поля `reason`

У каждой добавленной стадии есть поле `reason`, чтобы потом можно было объяснить пользователю, почему план построен именно так.

### Для `bootstrap`

Показывается:

- позиция пакета в порядке внутри SCC;
- какие внутренние зависимости уже были «раньше»;
- какие зависимости пришлось отложить;
- какие внешние зависимости есть у пакета.

### Для `full`

Показывается:

- какие зависимости уже используются в `full`-виде;
- какие ещё используются только в `bootstrap`-виде.

### Для `final`

Показывается:

- какие внутренние зависимости раньше были отложены;
- почему понадобилась финальная пересборка.

## Почему этот модуль нужен отдельно от `planner.py`

Такое разделение ролей делает архитектуру чище.

### `planner.py`

Отвечает за:

- построение графа зависимостей;
- поиск SCC;
- построение DAG между компонентами;
- выделение cycle-stage.

### `bootstrap_handler.py`

Отвечает за:

- выбор порядка внутри цикла;
- разрыв цикла на внутренние стадии;
- построение объяснимого внутреннего DAG.

Это удобно, потому что алгоритм развертывания цикла можно менять отдельно, не переписывая логику поиска SCC и построения общего плана.


## Итог

- `choose_bootstrap_order(...)` выбирает порядок пакетов внутри цикла;
- `expand_cycle_stage(...)` разворачивает одну циклическую компоненту во внутренние стадии;
- `apply_bootstrap(...)` применяет это ко всему плану.

после работы `bootstrap_handler.py` исходный план уже не содержит `cycle`-стадий, а содержит только ациклический набор стадий сборки.
