# Resolve: разрешение зависимостей

## Что делает модуль

`resolve.py` преобразует зависимости из spec-файлов (`BuildRequires`) в конкретные пакеты, которые необходимо собрать.

На вход модуль получает:
- множество пакетов, которые требуется собрать (`requested_to_build`);
- уже доступные в репозитории пакеты (`available_repo`);
- отображение зависимостей (`provides_index`);
- распарсенные spec-файлы (`specs`).

В результате работы:
- для каждой зависимости выбирается конкретный пакет-provider;
- строится множество пакетов, которые необходимо собрать (`final_to_build`);
- формируется граф зависимостей между пакетами (`resolved_deps`).

## Основная идея

Зависимости в spec-файлах задаются в абстрактном виде (capabilities), например `pkgconfig(zlib)`.

Одна такая зависимость может быть удовлетворена несколькими пакетами (provider’ами). Задача resolve — выбрать один конкретный пакет для каждой зависимости и раскрыть его собственные зависимости.

Алгоритм работает следующим образом:
- для каждого пакета из `requested_to_build` извлекаются его `BuildRequires`;
- для каждой зависимости выбирается один provider(на этапе MVP это делается практически не задумываясь);
- выбранный provider добавляется в множество сборки, если он отсутствует в репозитории;
- процесс повторяется для новых пакетов, пока не будет построено транзитивное замыкание зависимостей.

Таким образом, resolve выполняет обход графа зависимостей и строит замкнутое множество пакетов, необходимых для сборки.


## Как выбирается provider

Выбор выполняется в следующем порядке:

1. Если среди provider’ов есть пакет, уже присутствующий в `available_repo`, выбирается он.
   
   Это означает, что зависимость уже удовлетворена и не требует сборки.

2. Если среди provider’ов есть пакет, уже включённый в `final_to_build`, выбирается он.
   
   Это позволяет не добавлять лишние пакеты в сборку и переиспользовать уже выбранные.

3. Если среди provider’ов есть пакет, для которого существует локальный `.spec`-файл (то есть он присутствует в `specs`), предпочтение отдаётся ему.
   
   Это уменьшает вероятность выбрать пакет, который нельзя обработать в рамках текущего набора spec-файлов.

4. В остальных случаях выбирается один provider в детерминированном порядке (первый после сортировки).

Если provider’ов несколько, формируется предупреждение (`warning`), в котором фиксируется факт неоднозначности и выбранный вариант.

Если ни один provider не найден, формируется ошибка (`error`).


## Что считается результатом

Результатом работы resolve является набор структур, описывающих разрешённые зависимости и итоговое множество пакетов для сборки.

Функция возвращает:

- `resolved_deps: dict[str, set[str]]`

  Отображение вида `pkg → зависимости`, где для каждого пакета указаны конкретные пакеты, необходимые для его сборки.

  В этом отображении:
  - используются только реальные имена пакетов (без абстрактных зависимостей);
  - не включаются зависимости, уже удовлетворённые пакетами из `available_repo`.

- `final_to_build: set[str]`

  Итоговое множество пакетов, которые необходимо собрать.

  Это множество включает:
  - исходные пакеты из `requested_to_build`;
  - все транзитивные зависимости, которые отсутствуют в `available_repo`.

- `warnings: list[str]`

  Список некритичных проблем, возникающих в процессе resolve.

  Например:
  - наличие нескольких provider’ов для одной зависимости;
  - выбор одного из нескольких возможных вариантов.

- `errors: list[str]`

  Список критических ошибок.

  Например:
  - невозможность разрешить зависимость (отсутствуют provider’ы);
  - отсутствие spec-файла для требуемого пакета.

Наличие ошибок означает, что корректный план сборки построить невозможно.

## Текущие ограничения

Текущая реализация resolve использует упрощённую модель и не покрывает все возможные случаи, встречающиеся в реальных RPM-репозиториях.

В частности:

- не поддерживаются version constraints в зависимостях;

- не учитываются `Conflicts` и другие ограничения между пакетами;

- при наличии нескольких provider’ов выбирается только один, без глобального согласования;

- не выполняется перебор альтернативных вариантов (нет backtracking или подобного подхода);

- возможны ситуации, когда выбранный provider приводит к ошибке на более позднем этапе (например, отсутствует соответствующий spec-файл);

- выбор provider’а является локальным и эвристическим, а не оптимальным.

Такая модель является достаточной для MVP, но требует расширения для работы с реальными наборами пакетов.
