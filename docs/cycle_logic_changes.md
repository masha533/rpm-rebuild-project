# Изменения в логике обработки циклов и `available_repo`

## Требование

> Каждый компонент, сборка которого была запрошена явным образом, должен быть собран ровно один раз.

Из-за этого изменилась роль `available_repo`, поведение `planner.py` и использование `bootstrap_handler.py`.

---

## Главное изменение

Раньше логика могла воспринимать пакет из `available_repo` как пакет, который не нужно собирать.

Теперь это неверно.

Если пакет явно указан в файле `requested`, он должен попасть в план сборки, даже если он уже есть в репозитории.

То есть:

```text
requested = {cyc}
available_repo = {cyc}
```

означает:

```text
cyc нужно пересобрать
```

А старая версия `cyc` из репозитория может использоваться только для закрытия `BuildRequires`.

---

## Новая роль `available_repo`

`available_repo` теперь используется не для удаления пакетов из сборки, а для удаления рёбер зависимостей из графа сборки.

Ребро:

```text
A -> B
```

означает:

```text
A требует B для сборки,
поэтому новая сборка B должна быть выполнена раньше A.
```

Но если `B` уже есть в `available_repo`, то `A` может использовать старую версию `B`.

Тогда ребро в граф сборки не добавляется.

---

## Правило построения графа

В `planner.py` функция `normalize_graph(...)` теперь строит сразу две структуры:

1. `packages_graph` — зависимости, которые требуют новой сборки другого пакета;
2. `repo_requires` — зависимости, которые закрываются пакетами из репозитория.

Ребро `A -> B` добавляется в `packages_graph` только если:

- `A` зависит от `B`;
- `B` тоже находится в множестве пакетов, которые надо собрать;
- `B` отсутствует в `available_repo`.

Если `B` есть в `available_repo`, то зависимость записывается в `repo_requires`.

---

## Пример: пакет есть в репозитории и явно запрошен

Пусть есть spec-файл:

```spec
Name: cyc
BuildRequires: cyc
```

И входные файлы такие:

```text
available_repo = {cyc}
requested = {cyc}
```

Так как `cyc` явно запрошен, он должен быть собран.

Но его зависимость на самого себя можно закрыть старой версией из репозитория.

Поэтому результат будет таким:

```json
{
  "packages_graph": {
    "cyc": []
  },
  "repo_requires": {
    "cyc": ["cyc"]
  },
  "components": [
    {
      "packages": ["cyc"],
      "type": "acyclic"
    }
  ],
  "stages": [
    {
      "id": 0,
      "packages": ["cyc"],
      "type": "acyclic",
      "depends_on": [],
      "internal_edges": [],
      "bootstrap_required": false,
      "message": "Компонента не содержит циклов, пакет собирается обычным образом."
    }
  ]
}
```

Здесь важно:

- `cyc` не пропал из плана;
- `cyc` собирается ровно один раз;
- зависимость `BuildRequires: cyc` в `repo_requires`.

---

## Сообщение для такого случая

Если пакет есть в репозитории, но он явно указан в списке запрошенных пакетов, то пишем в `stderr`:

```text
[info] Пакет 'cyc' уже есть в репозитории, но он указан в списке запрошенных пакетов, поэтому будет пересобран.
```

Это сообщение означает:

```text
Пакет доступен в старой версии, но пользователь явно попросил пересобрать его,
поэтому он не удаляется из плана.
```

## Пример: пакет зависит от себя, но его нет в репозитории

Пусть spec-файл такой же:

```spec
Name: cyc
BuildRequires: cyc
```

Но входные файлы такие:

```text
available_repo = {}
requested = {cyc}
```

Теперь зависимость `cyc -> cyc` нельзя закрыть старой версией из репозитория.

Поэтому она остаётся в `packages_graph`:

```json
{
  "packages_graph": {
    "cyc": ["cyc"]
  },
  "repo_requires": {},
  "components": [
    {
      "packages": ["cyc"],
      "type": "cycle"
    }
  ],
  "stages": [
    {
      "id": 0,
      "packages": ["cyc"],
      "type": "cycle",
      "depends_on": [],
      "internal_edges": [["cyc", "cyc"]],
      "bootstrap_required": true,
      "message": "Эти пакеты образуют круговую зависимость. Такой этап не является готовым шагом сборки: он добавлен в вывод только для диагностики ошибки."
    }
  ]
}
```

Такой stage не считается готовым шагом сборки.

Он нужен только для диагностики: чтобы показать, какие пакеты образовали неразрешённый цикл.

## Ошибка для неразрешённого цикла

Если после учёта `available_repo` в плане всё ещё остаются стадии с:

```json

```

## Почему теперь цикл не разворачивается автоматически через `bootstrap_handler.py`

Раньше `bootstrap_handler.py` мог автоматически превращать `cycle-stage` в набор стадий:

```text
bootstrap
full
final
```

Например:

```text
cyc bootstrap
cyc full
cyc final
```

Но это противоречит уточнённому требованию:

```text
каждый явно запрошенный компонент должен быть собран ровно один раз
```

Кроме того, автоматическое bootstrap-разворачивание может создать план, который выглядит валидным, но фактически не сможет выполниться.

Например, если в spec-файле написано:

```spec
BuildRequires: cyc
```

и `cyc` отсутствует в репозитории, то первая сборка `cyc` не сможет начаться.


Поэтому сейчас `bootstrap_handler.py` не вызывается из `main.py`.

---

## Как теперь работает `main.py`

Основной сценарий такой:

1. читаются spec-файлы;
2. читается `available_repo`;
3. читается список явно запрошенных пакетов;
4. проверяется, что для каждого явно запрошенного пакета есть spec-файл;
5. зависимости разрешаются через `resolve(...)`;
6. строится план через `build_plan(...)`;
7. если в плане остались `cycle`-стадии, выводится ошибка;
8. если циклов нет, выводится готовый план.

---

## Проверка явно запрошенных пакетов

Если пакет явно запрошен, но для него нет spec-файла, сборка невозможна.

### Пакет есть в репозитории, но нет spec-файла

Сообщение:

```text
[error] Нельзя пересобрать пакет 'pkg': он есть в репозитории, но для него не найден spec-файл.
```

Смысл:

```text
Старая версия пакета есть, но пересобрать пакет без spec-файла нельзя.
```

### Пакет не найден ни в spec-файлах, ни в репозитории

Сообщение:

```text
[error] Пакет 'pkg' запрошен к сборке, но не найден ни среди spec-файлов, ни в репозитории.
```

Смысл:

```text
Система не знает, как собрать этот пакет, и не может использовать его старую версию.
```

## Что изменилось по сравнению со старой логикой

### Было раньше

```text
если пакет есть в available_repo:
    удалить его из requested_to_build
```

Из-за этого команда вида:

```text
available_repo = {cyc}
requested = {cyc}
```

давала пустой план:

```json
{
  "stages": [],
  "message": "Все пакеты уже доступны"
}
```

Теперь это считается неправильным, потому что `cyc` был явно запрошен к сборке.

---

### Стало сейчас

```text
если пакет есть в available_repo и в requested:
    пакет всё равно остаётся в плане сборки
    но зависимости на него могут закрываться старой версией из repo
```

То есть:

```text
available_repo не отменяет явную сборку,
а только помогает закрывать BuildRequires.
```

---

## Что считается успешным планом

Успешный план должен удовлетворять двум условиям:

1. каждый явно запрошенный пакет попадает в план сборки;
2. после учёта `available_repo` в плане нет циклических стадий.

Если эти условия выполнены, то выводит:

```json
{
  "warnings": [],
  "plan": {
    "packages_graph": {
      "cyc": []
    },
    "repo_requires": {
      "cyc": ["cyc"]
    },
    "components": [
      {
        "packages": ["cyc"],
        "type": "acyclic"
      }
    ],
    "stages": [
      {
        "id": 0,
        "packages": ["cyc"],
        "type": "acyclic",
        "depends_on": [],
        "internal_edges": [],
        "bootstrap_required": false,
        "message": "Компонента не содержит циклов, пакет собирается обычным образом."
      }
    ]
  }
}
```

---

## Что считается ошибкой

Ошибка возникает, если после учёта `available_repo` остаётся цикл.

Например:

```text
cyc -> cyc
```

при:

```text
available_repo = {}
requested = {cyc}
```

Такой план не может быть выполнен, потому что первая сборка требует уже существующий `cyc`.

---

## Итоговая логика

Коротко новая логика выглядит так:

```text
если пакет явно requested:
    он должен быть собран

если зависимость есть в available_repo:
    закрываем зависимость старой версией из repo
    не добавляем ребро в packages_graph

если зависимость не в available_repo, но пакет тоже строится:
    добавляем ребро в packages_graph

если после этого циклов нет:
    выводим план сборки

если после этого цикл остался:
    выводим ошибку unresolved_cycle
```
